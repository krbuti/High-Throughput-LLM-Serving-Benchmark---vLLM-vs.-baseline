# High-Throughput LLM Serving Benchmark: vLLM vs. Hugging Face baseline

Serve an open-weight LLM with **vLLM** on one cloud GPU and benchmark it under
concurrent load against a **plain Hugging Face Transformers** server. The
benchmark measures throughput (tokens/s), time to first token (TTFT) and
p50/p95/p99 latency.
It then isolates what **PagedAttention**, **continuous batching** and
**prefix caching** each contribute, and sweeps `--gpu-memory-utilization`,
`--max-num-seqs` and `--max-num-batched-tokens` to find the best
throughput/latency trade-off.

Both servers expose the same **OpenAI-compatible API**, so the same load
generator and a **LangGraph agent** can target either. Prometheus scrapes both,
and a provisioned Grafana dashboard shows the scheduler, KV cache and latency
live.

```
                 ┌───────────────────────── one GPU ─────────────────────────┐
 bench/loadgen ──►  vLLM  (:8000)  PagedAttention · continuous batching ·     │
 (async, N users)  │                 prefix caching · /v1/* · /metrics        │
 agent/ (LangGraph)│  — or —                                                  │
                   │  HF baseline (:8001) model.generate() · static batching ·│
                   │                 /v1/* · /metrics                         │
                   └──────────────────────────┬────────────────────────────────┘
                                              │ scrape every 5 s
                                   Prometheus (:9090) ──► Grafana (:3000)
```

## Repository layout

| Path | What it is |
|---|---|
| `servers/hf/server.py` | Baseline: FastAPI + `transformers` `generate()`, OpenAI-compatible, streaming, static batching, Prometheus metrics |
| `bench/loadgen.py` | Async load generator: closed-loop (N concurrent users) or open-loop (Poisson req/s), streams SSE to measure TTFT, inter-token latency and end-to-end latency |

## Quick start

You need a Linux GPU VM (e.g. GCP `g2-standard-8` with an L4, AWS `g5.xlarge`
with an A10G, or any A100/H100) with the NVIDIA driver, Docker and the
NVIDIA Container Toolkit installed.

```bash
git clone https://github.com/krbuti/High-Throughput-LLM-Serving-Benchmark---vLLM-vs.-baseline.git
cd High-Throughput-LLM-Serving-Benchmark---vLLM-vs.-baseline
cp .env.example .env            # pick MODEL, set HF_TOKEN for gated models
make install                    # client-side deps (no GPU needed)
make test                       # 21 tests against the mock server (+5 HF-server tests if torch is installed)
```

**Serve and watch it live**

```bash
make up-vllm                    # vLLM on :8000, Prometheus :9090, Grafana :3000
curl localhost:8000/v1/completions -H 'content-type: application/json' \
  -d '{"model":"Qwen/Qwen2.5-3B-Instruct","prompt":"PagedAttention is","max_tokens":32}'
make bench-vllm                 # quick load test, watch Grafana while it runs
make agent                      # chat with the LangGraph agent
```

Open `http://<vm-ip>:3000` (or tunnel it with `ssh -L 3000:localhost:3000 …`).
The **LLM Serving** dashboard is the home page.

**Run the full study**

```bash
make down                       # the sweep needs the whole GPU
make sweep                      # builds the HF image, runs configs/sweep.yaml (~1.5-3 h on an L4)
make report                     # results/report/REPORT.md + PNG charts
```

The sweep skips experiments whose `results/<name>.json` already exists, so you
can stop and resume it (spot instances, OOMs). Use `--only 'vllm_mem_*'` to run
a subset and `--force` to redo one.

## What is measured, and how

All requests use greedy decoding with **`ignore_eos`**, so every request
produces exactly `output_len` tokens and both servers do identical work.
Token counts come from the server's `usage` field (`stream_options.include_usage`).

| Metric | Definition |
|---|---|
| Output throughput | total generated tokens / wall-clock time of the run |
| TTFT | request sent → first non-empty streamed chunk (includes queueing + prefill) |
| TPOT | (e2e − TTFT) / (output tokens − 1), the decode speed one user sees |
| ITL | gap between consecutive streamed chunks |
| E2E latency | request sent → stream closed; reported as p50/p95/p99 |

Closed-loop mode (`--concurrency 1 4 16 64 128`) models N users who each send
their next request as soon as the last one returns. Open-loop mode
(`--request-rate`) fires Poisson arrivals no matter how slowly the server
responds, which shows queueing collapse.

### The experiments (`configs/sweep.yaml`)

| Group | Configs | What it isolates |
|---|---|---|
| Baseline | `hf_sequential`, `hf_static_bs8`, `hf_static_bs32` | Transformers `generate()`. Sequential, or static batches that run to completion with padded, contiguous KV caches |
| vLLM default | `vllm_default` | 0.90 GPU memory, 256 max sequences, prefix caching on |
| **Continuous batching** | `vllm_seqs_{1,8,32,128}` + default | `max-num-seqs=1` turns vLLM into a sequential server with the same kernels; widening the batch shows what iteration-level scheduling buys |
| **PagedAttention / KV memory** | `vllm_mem_{0.40,0.55,0.70,0.95}` | GPU memory → number of KV blocks (logged as `kv_cache_tokens` / `max_concurrency`) → how many sequences can run before queueing or preemption |
| Chunked prefill | `vllm_batched_tokens_{2048,8192}` | Token budget per scheduler step: TTFT vs inter-token latency |
| **Prefix caching** | `vllm_prefix_on`, `vllm_prefix_off`, `hf_prefix_bs8` | 2048-token prompts of which 1792 tokens are shared. Cached KV blocks skip most of the prefill |

**A note on PagedAttention.** vLLM has no switch to turn PagedAttention off,
so its effect can't be measured as a clean on/off ablation. The study measures
it two ways instead:

1. **Against the baseline.** The HF server keeps a dense KV cache per batch,
   padded to the longest sequence and allocated for the whole batch's lifetime.
   vLLM allocates 16-token blocks on demand. The HF static-batch runs show the
   cost: batch sizes beyond what memory allows hit OOM, and short sequences
   hold memory until the longest one finishes.
2. **Through KV capacity.** The `vllm_mem_*` sweep records how many tokens of
   KV cache vLLM allocated (from its startup log) and the resulting maximum
   concurrency, and plots throughput and p95 latency against them.

### Tuning knobs, and how they show up

| Knob | Higher means | Watch |
|---|---|---|
| `--gpu-memory-utilization` | more KV blocks → more concurrent sequences, fewer preemptions | Grafana *Paged KV cache usage*, *Preemptions* |
| `--max-num-seqs` | wider decode batch → more tokens/s, but each step gets slower (higher TPOT) | *Scheduler: running vs waiting* |
| `--max-num-batched-tokens` | larger prefill chunks → lower TTFT, but decoding users stall during the chunk (ITL spikes) | *Inter-token latency* |
| `--enable-prefix-caching` | shared prompt prefixes skip prefill | *Prefix cache hit rate* |

`make report` picks the **best config under a latency budget**
(`--latency-slo`, default p95 ≤ 10 s) and lists the Pareto frontier of
throughput vs p95 latency.

## The baseline server

`servers/hf/server.py` is a fair, reasonably good HF deployment, not a straw
man:

- bf16 weights with SDPA attention
- incremental detokenisation, the same scheme TGI and vLLM use
- **static batching**: requests that arrive within `HF_BATCH_WAIT_MS` are
  left-padded into one `generate()` call, up to `HF_MAX_BATCH_SIZE`
- a custom `BaseStreamer` streams every sequence in the batch to its own client
  as tokens are produced
- each request's own `max_tokens`, EOS and `stop` strings are honoured inside a
  shared batch; a stopping criterion ends the batch once all of its sequences
  are done
- a disconnected client frees its batch slot

Tests verify that a batched, streamed request returns exactly the same greedy
output as the same request run on its own. Its Prometheus metrics (`hf_*`)
mirror vLLM's (`vllm:*`), so the dashboard can show both side by side.

What it can't do is what the benchmark is about: a new request can't join a
batch already running, and memory is reserved for padding.

## LangGraph agent

```bash
OPENAI_BASE_URL=http://localhost:8000/v1 python agent/agent.py \
  -q "Which vLLM config gave the most throughput with p95 latency under 5 s, and how much faster is it than HF sequential?"
```

The agent prints each tool call as it makes it, for example:

```text
  -> benchmark_results({"config_filter": "vllm", "max_p95_latency_s": 5})
  -> benchmark_results({"config_filter": "hf_sequential"})
  -> calculator({"expression": "<vllm tok/s> / <hf tok/s>"})
```

The agent is a hand-written LangGraph `StateGraph` (agent node → `ToolNode` →
agent, stopped by `tools_condition`). It calls vLLM through `ChatOpenAI` with
only `base_url` changed. vLLM parses tool calls with
`--enable-auto-tool-choice --tool-call-parser hermes` (Qwen2.5 format; use the
parser that matches your model). Tools: `calculator`, `benchmark_results`
(queries `results/`), and `live_server_metrics` (reads vLLM's `/metrics`).

## Development without a GPU

```bash
python -m bench.mock_server --port 8000 --slots 8 &
python -m bench.loadgen --base-url http://localhost:8000 --model mock --concurrency 1 8 32
```

The test suite starts the mock server itself. If `torch` and `transformers`
are installed, it also runs the real HF server on CPU with a tiny randomly
initialised Qwen2 model built on the fly (no downloads). Those tests check
batching correctness, stop strings, cancellation and the API surface.

## Changing the model or GPU

- **7B on an A100/H100/L40S:** set `model: Qwen/Qwen2.5-7B-Instruct` in
  `configs/sweep.yaml` (and `MODEL` in `.env`), and raise the HF batch sizes.
- **24 GB GPU:** keep the 3B model so the memory sweep (0.40–0.95) leaves room
  for a KV cache after the weights load; a 7B model's ~15 GB of weights won't
  load at 0.40.
- **Gated models (Llama, Gemma):** set `HF_TOKEN`.
- vLLM image and flags are pinned in `configs/sweep.yaml` / `docker-compose.yml`.
  The Grafana queries cover the metric names of both older and newer vLLM
  releases.
